# Источники обновлений

Клиент проверяет две вещи при открытии главного окна: версию **сервера** и версию
**приложения**. Оба списка берутся из релизов GitHub, никаких JSON-файлов на стороне
автора больше нет (`releases1/*.json` остались только для старого MatriX-клиента).

## Два репозитория

| Что | Репозиторий | Тег | Ассеты |
|-----|-------------|-----|--------|
| Клиент (APK) | `YouROK/TorrServe` | `Silo.N.Client` | `TorrServe_Silo.N.Client.apk`, `SHA256SUMS.txt` |
| Сервер (бинарник) | `YouROK/TorrServer` | `Silo.N` | `TorrServer-android-arm7`, `-arm64`, `-386`, `-amd64`, `SHA256SUMS.txt` |

`MatriX.*` и старое `1.2.*` игнорируются: берутся только теги с префиксом `Silo.`,
а клиентские отличаются суффиксом `.Client`.

## Почему Atom-лента, а не API

На части ТВ-сетей (и на тестовой приставке это подтвердилось) провайдер кеширует
ответы `github.com` и `api.github.com`: клиент получал список релизов, которому уже
сутки, при свежем заголовке `Date` и даже при метке времени в URL. Кроме того, у API
без токена лимит 60 запросов в час на IP.

Поэтому списки берутся из `https://github.com/<repo>/releases.atom` через `XmlPullParser`
(`server/api/GithubReleases.kt`): там актуальные теги, дата и текст релиза, лимита по IP нет.
Ссылки на файлы не запрашиваются отдельно — имена ассетов известны заранее, поэтому URL
строится как

```
https://github.com/<repo>/releases/download/<tag>/<asset>
```

## Когда идут проверки

Никакого таймера «раз в 5 минут» нет — проверка запускается по событиям:

- **при запуске приложения** (первый `onResume` главного окна) — обновление клиента;
- обновление локального сервера — один раз за запуск, но только после первого успешного
  ответа сервера: на холодном старте приложение само поднимает сервер, поэтому проверка
  из `onResume` попадала на ещё не запущенный сервер и молча пропускалась;
- **кнопкой «Проверить обновление»** в настройках — принудительно, для клиента;
- при повторном открытии главного окна в том же процессе повторной проверки нет
  (флаг `updateChecked` живёт до перезапуска приложения) — обновите экран или
  перезапустите приложение, чтобы увидеть только что опубликованный релиз.

Кеши:

- Atom-лента кешируется в памяти на 15 минут (на репозиторий).
- Автоматическая проверка приложения — не чаще раза в 6 часов (`Prefs.updateCheckedAt`).
- Кнопка «Проверить обновление» обходит кеш, но не чаще раза в минуту:
  в пределах минуты отдаётся уже известный результат (`Prefs.appUpdateLatestTag`).
- Ошибка сети не сбрасывает отметку времени: неудачная проверка повторится при
  следующем запуске, но не будет дёргать GitHub в цикле.
- Обновление сервера показывается тостом один раз за запуск и только когда сервер
  локальный (для внешнего сервера версию обновляет его владелец).

## Где видна версия сервера

- **Внизу бокового меню**, под именем пользователя (`owner`), рядом с адресом:
  `http://127.0.0.1:8090 (Silo.3)` — версия из `/api/system/version`
  (кеш по адресу: `Prefs.serverVersion()`). Эндпоинт защищённый: клиент отправляет
  токен активной сессии, иначе сервер с паролем владельца отвечает `401`.
- **Настройки → Локальный сервер**: `Установлен: TorrServer-android-arm7 (Silo.3)` —
  имя файла релиза и версия установленного бинарника; если сервер ещё не запускался,
  в скобках `версия неизвестна`.

При установке из папки проверяется архитектура бинарника по ELF-заголовку: файл для
`arm64`/`amd64` на 32-битной приставке отклоняется с понятной ошибкой, а не тихо
ломает запуск сервера.

## Установка APK

1. Приложение показывает диалог: версия, «что нового» (текст релиза из Atom), кнопки
   «Обновить»/«Позже».
2. «Обновить» скачивает APK в `cacheDir/updates` с прогрессом и сверяет SHA-256
   с `SHA256SUMS.txt` того же релиза (если файла в релизе нет — проверка пропускается).
3. Файл отдаётся системному установщику через `FileProvider` (`${applicationId}.provider`,
   `res/xml/file_paths.xml`, разрешение `REQUEST_INSTALL_PACKAGES`). Если установка
   из неизвестных источников не разрешена, открывается экран разрешения для приложения.

## Порядок выпуска

1. Собрать и проверить изменения локально (`./build.sh`).
2. Поставить тег и запушить его — это единственное, что задаёт версию:

   ```bash
   git tag Silo.2.Client && git push origin Silo.2.Client
   ```

3. Workflow `.github/workflows/release-apk.yml` соберёт `TorrServe_Silo.2.Client.apk`
   (`versionName` = тег, `versionCode` = N из тега), подпишет ключом из секретов,
   посчитает `SHA256SUMS.txt`, создаст релиз и сгенерирует к нему описание
   («What's Changed») — оно попадёт в Atom-ленту и будет показано в приложении.
4. Клиент увидит обновление при следующем запуске (или по кнопке в настройках).

Важно: обновляться «поверх» можно только сборкой, подписанной тем же ключом.
Debug-сборка и релизный APK несовместимы (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) —
для перехода на релизные сборки приложение нужно один раз переустановить.
